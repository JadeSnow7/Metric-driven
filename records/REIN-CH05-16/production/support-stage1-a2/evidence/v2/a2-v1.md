# A.2 用枚举与类型表达运行状态

**状态：已完成本阶段材料｜限时免费**

第 05、06 章的循环同时维护“程序现在是什么状态”和“最后为什么停下”。TypeScript 用判别联合表示事件，Rust 用带数据的枚举表示同一组事件。两者都能在 JSON 中表达共同观察结果，但编译期类型并不会替代运行时校验。

## TypeScript：以 `type` 判别事件

`ts/src/rein/loop.ts` 将状态和停止原因定义为字符串联合：

```ts
export type LoopState = 'running' | 'completed' | 'failed'
export type StopReason = 'final_answer' | 'empty_final' | 'model_error' |
  'max_turns' | 'tool_budget_exhausted' | 'duplicate_action' | 'cancelled' | 'timeout'
export type LoopEvent =
  | { readonly type: 'model_requested'; readonly turn: number; readonly messages: readonly Message[] }
  | { readonly type: 'tool_result'; readonly turn: number; readonly toolCallId: string; readonly result: ToolResult }
  | { readonly type: 'action_skipped'; readonly action: 'model' | 'tool'; readonly reason: StopReason }
  | { readonly type: 'stopped'; readonly state: Exclude<LoopState, 'running'>; readonly reason: StopReason }
```

`type` 是判别字段：读取事件时先判断 `event.type`，TypeScript 才能知道本分支有哪些字段。`readonly` 约束编译期赋值，不会阻止不受类型检查的 JavaScript 修改对象，也不会验证外部 JSON。`LoopResult` 的 `answer` 和 `error` 是可选字段，因此取消或失败结果不应被代码假定有答案。

合同中的 `ToolResult` 也采用布尔值加可选字段：

```ts
export interface ToolResult {
  readonly toolCallId: string
  readonly ok: boolean
  readonly output?: string
  readonly error?: { readonly code: string; readonly message: string }
}
```

运行时的 `dispatchReadonly` 仍需检查工具名、参数类型、路径边界和文件错误；`additionalProperties: false` 只是发给模型的 schema 声明。外部模型响应先经过 JSON 解析和字段检查，不能因为接口声明了 `ModelTurn` 就跳过验证。

## Rust：枚举携带状态和数据

`rust/src/rein/loop.rs` 用 serde 属性把 Rust 枚举转换成共享 wire 值：

```rust
#[derive(Clone, Debug, Serialize, Deserialize, PartialEq, Eq)]
#[serde(rename_all = "snake_case")]
pub enum StopReason {
    FinalAnswer,
    EmptyFinal,
    ModelError,
    MaxTurns,
    ToolBudgetExhausted,
    DuplicateAction,
    Cancelled,
    Timeout,
}
```

事件枚举用 `#[serde(tag = "type", rename_all = "snake_case")]`，例如 `ToolResult` 携带 `turn`、`call`、`tool_call_id` 和 `result`，`ActionSkipped` 携带可选 `call_id` 与停止原因。Rust 的 `match` 要覆盖枚举变体，编译器能发现新增状态遗漏；`Option<String>` 明确答案和错误可能不存在。`serde(rename = "toolCallId")` 又让 Rust 字段落成与 TypeScript 相同的 JSON 键。

## 同一个 JSON，不同的边界

两种实现都把实际结果放入消息和事件：

```json
{"type":"tool_result","turn":1,"toolCallId":"read-1","result":{"ok":true,"output":"marker: README alpha\n"}}
{"type":"stopped","state":"completed","reason":"final_answer"}
```

`snake_case` 的停止原因和 `camelCase` 的关联字段是 wire 合同；事件的完整字段仍以各语言实现为准。序列化成功只说明值能编码，不能证明工具路径安全、模型回答非空或动作真的执行。TypeScript 依靠运行时分支和测试，Rust 依靠类型、serde 解码和运行时检查共同完成边界。

例如，`LoopEvent` 的 `readonly`、Rust 的 `Vec<Message>` 和 `Option` 都不自动阻止恶意或损坏的外部输入。真正的验证点仍在 adapter 解析、`dispatchReadonly` 的参数/路径检查和循环停止分支。把编译通过写成“已经完成任务”，会丢掉这些运行时条件。

## 跟做：把状态和事件一起读

```bash
export REIN_A2_DIR="$(mktemp -d)"
printf 'marker: README alpha\n' > "$REIN_A2_DIR/README.md"
npm run ch06:offline --workspace ts -- normal "$REIN_A2_DIR"
cargo run --manifest-path rust/Cargo.toml --example ch06_loop -- normal "$REIN_A2_DIR"
```

对比两份 JSON：正常结果有 `state: "completed"`、`reason: "final_answer"`；把场景改为 `zero` 会得到 `failed/max_turns`，但 CLI 仍可正常退出并打印结果。阅读事件时先看 `type`，再看对应字段；不要把 `answer`、`tool_result` 或 `toolCallId` 当作每个状态都必然存在。
