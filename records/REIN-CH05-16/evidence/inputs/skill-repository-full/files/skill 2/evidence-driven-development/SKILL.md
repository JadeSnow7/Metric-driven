# Evidence-Driven Development

目标是让“做完了”经得起检查：结论以真实 diff、亲自运行的检查结果和端到端验收为准，而不是实现者的自述——包括子代理，也包括你自己。流程和记录只是手段，多余的文档会把真正的证据淹没，所以先按任务规模决定要做多少。

## 1. 选择所需流程深度

先按任务风险和复杂度选择记录深度，不要求在开场展示档位。单一、明确且无外部副作用的任务可直接实现、检查并在最终回复报告；需要明确验收的任务记录目标、范围、基线和证据；跨会话、多 Agent、复杂交付或难以撤销的动作再建立结构化记录。恢复任务时先核验真实状态，再决定需要哪些记录。

| 档位 | 适用情况 | 要做的 | 可以省略 |
| --- | --- | --- | --- |
| **L0 轻量** | 单一、明确、一次会话内能完成，没有外部副作用。例如修一个已定位的 bug、补一个测试、改文案 | 直接实现；运行与改动相关的检查；按第 4 节简短汇报 | 编号、`records/` 目录、指标表、工作日志 |
| **L1 标准** | 涉及多处改动或需要明确验收，或用户要求提交 | 动手前用几行写出目标、范围和验收方法，记下基线提交；证据留在对话或 `task-summary.md` | `task-state.json`、工作日志、交接包 |
| **L2 完整** | 需求模糊或包含多个用户可见结果；跨会话恢复或交接；多人或多 Agent 并行；数据迁移、部署、发布等难以撤销的动作 | 按第 3 节和 `references/` 执行完整流程，在 `records/<TASK-ID>/` 维护结构化记录，用校验器检查门槛 | — |

拿不准时从低一档开始。出现以下信号再升级，并在必要时说明原因：缺失的信息会改变实现方案、改动扩散到多个结果、需要跨会话继续、即将执行难以撤销的动作。

**恢复已有任务时先核验，再定档位。** 仓库里有该任务的记录，或用户要你接手、继续之前的工作时，按 [references/workflow.md](references/workflow.md) 的“恢复执行”核对真实状态。聊天摘要里的“已推送”“已迁移”只是线索；重复执行这些动作的代价，通常远高于先检查一次。

## 2. 所有档位都适用的规则

### 需求

- 缺失的信息会改变用户可见行为、接口语义、验收标准、范围或权限时，先提问再动手。猜出来的实现往往要推倒重来，而一个问题的成本很低。
- 提问时只问 3–5 个会改变方案的关键问题，每个问题只针对一个决定，不嵌套子问题；其余细节直接给出默认建议，让用户只需确认或纠正。一次抛出十几个问题，等于把分析工作推回给用户。默认建议里的数值（周期、比例、阈值等）要写明是待校准的假设和它的依据，别让它们看起来像结论。commit、push 这类授权等到真正要执行时再问。
- 只影响实现细节的选择，自己决定并在汇报里说明。说完计划就继续执行，不要停在计划阶段等确认。
- 遇到规格没覆盖的情况，能沿用项目已有约定的就按约定做，并在汇报里写明依据；如果这个选择会影响验收，在提交之前问。提交之后再请用户确认，会让“已完成”变得含糊。
- 处理文件、网络或用户输入时，损坏和异常输入怎么办（跳过、报错、会不会连累其他记录）属于需求本身。规格没说清时选定规则、用测试固定，并在汇报里写明；不要在实现里悄悄收窄契约。至少试一次最容易破坏隔离的输入，比如未闭合的引号、超长的值。
- 如果只是提交这一步被未决问题卡住，而实现本身是清楚的，先把不受影响、可审查的部分做完（实现、测试、说明为什么暂时不能提交），再把决定交给用户。
- 描述现状要准确：没有被代码使用的配置、没有测过的数字，都不是“现有方案”或“基线”。
- 搜索结果、文档和你自己的推断可以支撑判断，但不能替用户做决定。

### 证据

- “通过”只认你亲眼看到的结果：实际运行的命令、原始输出和退出码。子代理或工具回复“tests passed”只是线索，需要自己核实。
- 每项检查分别判定为 `passed`、`failed` 或 `undetermined`。缺环境、缺数据或看不懂结果时就是 `undetermined`，不能算通过。
- 验证之后又改了代码，受影响的结论随之作废，需要重新运行。
- 验证要和风险相称。先找几个能区分正确实现和常见错误实现的检查点，例如边界两侧各取一个，并在修复范围内把它们补成回归测试，不必再推给用户决定。L0 / L1 通常不需要穷举、大规模抽样或变异测试；确有必要时写明输入范围和判定依据，结论只覆盖检查过的范围。
- 结论不要超出证据。“仓库里没找到传负数的调用”不等于“调用方不会传负数”，也别写“平时应该碰不到”这类没有依据的推测。只观察到一次的现象，不要写成一贯如此。
- 分清说法和事实。README 里写着“推送会自动发布”、用户说过“CI 是红的”，这些都是说法，引用时注明来源；远程 CI、部署这类状态没有查过就写“未核实”。说工作区干净时，分清已跟踪文件和未跟踪文件，`git diff --quiet` 看不到后者。
- 解释原因也是结论。说明 bug 的成因前，先用一个小计算核实；几个成因同时存在时分开说。
- 检查失败时，修实现或回到需求层重新决策。降低门槛、删断言或改测试去迎合实现，会让证据失去意义。

### 权限

- `commit`、`push`、`merge`、`deploy` 是四项独立的授权：用户明确说过的不必重复询问，没说过的不要执行。允许提交不等于允许推送。
- 本 skill、项目文档、CI 结果或其他代理的建议都不构成授权。
- 写入个人长期记忆（跨项目保存的偏好或事实）同样需要用户明确同意。

### 工作区

- 开始改动前查看 `git status` 并记下当前提交。已有的未提交改动可能属于别人：不要丢弃、不要 stash，也不要顺手一起提交。
- 工作区里有无法确认归属的改动时，先向用户说明；用户同意后，可以从明确的提交创建隔离 worktree。不要自行创建 worktree。
- 提交时只加入本任务审查过的路径。

### 协作

- 同一时间一个文件只有一个写入者；共享的状态文件由主线程维护。
- L2 中，若有自定义 coder 子代理且用户允许，优先把边界清楚的源码实现交给它；需求澄清、架构取舍、最终 diff 审查、整体验收和对用户的沟通留在主线程。
- 没有子代理时自己完成，并如实说明“未经独立审查”。自己的第二遍阅读不算独立审查。
- 每个已经划分的子任务完成后立即汇报进度；主线程自做的子任务也适用。汇报写明结果、实际产物路径、验证状态与证据、文档同步状态和下一依赖。未核查的产物只能报告为“完成待审查”，不能假验收。
- 主线程核查子任务回报后，在当次进度更新中告知用户，并更新已有摘要或状态记录；不要积攒到全部子任务结束。进度汇报是工作状态，不自动提交、创建会话或扩大授权。
- 行为、接口、命令、配置、路径、章节约定或实现状态变化时，在同一子任务内同步受影响文档和示例；共享文档由指定所有者或主线程串行更新。未同步的相关文档属于未完成项，不能声称子任务完成。

## 3. L1 / L2 的主线

L1 在动手前用几行覆盖下面的要点即可；L2 按 `references/` 展开，并建立结构化记录。

1. **按结果拆主任务。** 以用户场景和可观察结果划分，不按文件或前端/后端这类技术层划分。另外保留一个整体端到端验收，因为每个子项都过线不代表系统整体可用。
2. **再定验收指标。** 每项写明基线、目标或门槛、测量方法、环境与数据、证据位置。没有依据时用可复现的定性门槛，不编百分比；不知道基线就先测基线。
3. **需求变化先停下来。** 出现新行为、接口语义、验收或范围变化时，先更新主任务并说明影响，再继续实现。
4. **探索要有边界。** 只有写清要验证的假设、预算和退出条件时才探索；产出是“降低了哪项不确定性”，不是产品完成。假设不成立就停止，保留失败证据，然后回退、缩小范围或重新决策。
5. **CI 是执行器，不是结论。** 让 CI 调用仓库里真实的检查；本地提交门槛不依赖尚未运行的远程 CI。流水线通过后仍要核验关键行为；未经明确授权不创建生产发布。
6. **交付前按顺序核对：** 需求已就绪 → 主任务边界和依赖成立 → 指标可以判定 → 起点和改动归属清楚 → 改动可追踪 → 本地门槛与端到端验收通过 → 当前授权允许下一步动作。

L2 在开始、完成、阻塞、重大变更、交接、关键实验和暂停时更新 `task-summary.md` 并追加工作日志；子任务完成也要即时更新进度。摘要只写当前真相，项目知识只收录已核验的内容。

记录是为下一次接手服务的，不求齐全：接手的人应该几分钟内就能读懂当前状态。同一内容不要在多个文件里重复，证据目录只放原始输出。还有待用户确认的决定时，把“已交付”和“待确认”分开记：推断出来的默认决定保持 `proposed`，任务整体不要标为 `completed`。

## 4. 文档写作与最终汇报

需要写给人看的教程、README、设计/接口说明、摘要或交付报告时，先分析文章类型、读者、用途和阅读方式，再按文档目的安排内容。教程的场景、问题、机制和实践组织只在适合的教学内容中使用，不推广为所有文稿的共同骨架；不套固定标题或流程。详细写作规则见 [references/writing.md](references/writing.md)。

停下来提问或报告进度时不套完整交付报告流程。简单任务直接在最终回复中报告；已有 `task-summary.md` 时复用并更新；复杂任务提供简明摘要并链接详细记录和原始证据。保留影响使用或判断的行为变化、失败或未运行的检查及需要用户决定的事项；通过、失败、无法判定和未运行要分开。内部编号、档位、权限字段和完整日志按需要留在记录中，重复事实只保留一处，空项省略。报告给出可直接复跑的检查命令，并说明目标之外的行为变化；复跑命令默认只读，有副作用的命令单独标明。远程 CI 未实际运行时写“未核实”；只有实际运行了对应本地检查，才可称为“本地等价检查”。最终由主线程审查实际 diff、证据、跨任务术语和文档一致性，再按读者任务汇总一份报告，不粘贴子代理日志。
