# 人类可读的交付报告

本文件只在需要写交付报告时读取。它规定报告如何帮助读者理解结果，不规定固定标题，也不以关键词或篇幅单独判断质量。

## 四步流程

1. **先确定读者的任务。** 写作前明确读者需要理解什么、判断什么或决定什么。面向使用者先解释行为影响，面向审查者先交代依据和未决风险；不要把内部记录结构当成读者目标。
2. **整理可核对的事实。** 从实际改动、验证结果和任务状态中提取事实，标明它来自观察、他人报告还是推断。把失败、未运行、证据过期和仍缺的决定保留下来；没有证据的内容不要补写成结论。
3. **按读者的阅读顺序说明。** 先写结果及其影响，再解释关键改动、为什么这样改和哪些证据支持它，最后写未完成事项、限制或下一步。遇到复杂机制，从具体问题或熟悉场景进入；必要时用简短的前后对照解释因果。
4. **交付前核对。** 检查关键事实、行为变化和限制是否准确且足够；删掉重复事实、无关内部术语和不影响判断的过程；确认结果、原因、依据和下一步的顺序自然。缩短时不能隐藏失败、未运行检查或需要用户决定的事项。

## 选择报告载体

- 简单任务直接在最终回复中报告。
- 已有 `task-summary.md` 的任务更新该摘要，让它保持当前真相；历史过程追加到 `work-log.md`，原始输出放在 `evidence/`。
- 复杂任务提供简明摘要，并链接详细记录和原始证据。只在确实需要下一位执行者继续工作时创建交接包。

报告可使用项目已有标题，但“结果”“改动”“交付动作”等部分不要重复同一事实。内部编号、档位、权限字段和完整日志按需要保留在记录中；只有当它们影响读者判断时才在报告中解释。
