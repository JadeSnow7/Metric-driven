# 按文体组织写作

本文件在需要写教程、README、设计/接口说明、工作摘要或交付报告时读取。它规定文档如何帮助读者理解和使用结果，不规定固定标题，也不以关键词或篇幅单独判断质量。

## 写作方法

先分析文章类型、读者、用途和阅读方式，再决定叙述组织。不必机械展示这一步或停下来提问；已有上下文足够时直接判断。共用要求是准确、直接、可读，必要条件就近说明，并让文档与代码、命令和输出保持一致。下表是常用类型的决策参考，不是每篇文章的固定结构：

| 类型 | 读者目的 | 适合的组织重点 |
| --- | --- | --- |
| 教程 | 学习、跟做并通过观察理解 | 承接前置知识，从具体场景或小实验进入，解释原因、机制和实践结果 |
| 操作指南 | 完成一项具体操作 | 前提、步骤、参数、预期输出和故障处理 |
| 参考型技术文档 | 查询准确契约 | 对象、参数、返回值、错误、版本和示例 |
| 设计说明 | 理解方案与取舍 | 问题约束、方案机制、取舍依据和影响 |
| 工作进度/交付报告 | 判断结果与下一步 | 结果、影响、证据、未完成事项和待决事项 |

README 通常承担入口、快速上手或功能概览，按其实际定位组织，不仅按文件扩展名判断。混合文档可按章节或段落角色切换；其他文章按自身目的组织，不必强塞进表中的类型。

写清具体行为、原因与结果：说明新增或改变了什么，以及它解决哪个具体问题。只有在实际机制需要时，才展开对象、路由条件、状态变化或结果生成过程。必要时用前后对照、输入输出或最小示例连接原因与做法。已核验的事实直接陈述；精度用对象、条件、版本和输入范围表达，不无理由叠加泛泛限定词。

涉及命令、文件、接口或输出时，沿着读者实际路径核对一遍：示例创建的文件、后续读取的路径、参数和预期输出必须彼此一致。样本中的具体技术目标可以作为叙事方式参考，不能因此写成当前已实现或已验证的能力。

把证据分层。工作底稿中分清亲自观察、他人报告和代理推断，并记录来源与核验时间；正文只在影响读者判断的地方说明来源和不确定性。影响使用或判断的失败、未运行检查、必要条件和未决决定要保留，且就近写在相关结论旁。相同状态集中说明一次，不在每段或每篇末尾机械追加限制。

交付前核对关键事实、行为变化、因果关系、引用和当前实现；删去重复内容、无关内部术语和不影响判断的过程。不制定机械禁词表。不要发明事实、把计划写成已实现、夸大承诺或复制样本中的技术结论。限制只写实际影响使用或判断的事项；没有这类事项时省略该段。

代码行为或文档所述约定变化时，在同一子任务中更新受影响的文档和示例，不等到最终交付；没有受影响的文档时无需新造。共享文档无法直接修改时，回报具体待改项，由所有者同步后再收尾。后续实现再次变化时，更新关联说明并标记失效检查，重新核验受影响内容。

## 选择报告载体

- 简单任务直接在最终回复中报告。
- 已有 `task-summary.md` 的任务更新该摘要，让它保持当前真相；历史过程追加到 `work-log.md`，原始输出放在 `evidence/`。
- 复杂任务提供简明摘要，并链接详细记录和原始证据。只在确实需要下一位执行者继续工作时创建交接包。

文档可使用项目已有标题，但各段应服务于读者任务，不重复同一事实。内部编号、档位、权限字段和完整日志按需要保留在记录中；只有当它们影响读者判断时才在正文中解释。
