# 第二轮报告：headless 原生加载复跑

计划见 [PLAN.md](PLAN.md)。每组每个任务 5 个样本，以下是在这些样本上观察到的频数，不作因果推断或普遍结论。

## 结论

- **完成情况**：20 次全部完成，没有超时或出错。20/20 产品检查满分，两个陷阱（未接入的 stub、合法空操作 `sync`）被全部识别。和第一轮一样，产品质量上看不出两组差异。
- **L1 先写并运行新检查（P2）**：A 组 0/5，B 组 5/5。与第一轮方向一致，两轮合计 A 0/7、B 7/7。
- **L1 修改产品前至少运行过一次（P1）**：A 组 3/5，B 组 5/5。A 组有 2 次是直接写 `export.py`，之后才第一次运行任何东西。第一轮没有出现这种情况（A 组 2/2）。
- **L0 没有流程差异**：两组 5/5 都先复现再修改，0/10 创建结构化记录。B 组的轮次和成本中位数略低，但样本少、波动大，不作结论。
- **成本**：L1 上 B 组更贵更慢，成本中位数 $0.348 对 $0.306（+14%），耗时中位数 50.6s 对 39.9s（+27%），轮次中位数 10 对 7。多出来的部分来自"先写测试、运行、再实现"的额外步骤。
- **Skill 文件读取**：20 次运行都没有用 Read 打开任何 Skill 文件，包括 references。原生加载只注入 SKILL.md 正文，执行者也没有按需深入。这与第一轮"只读 SKILL.md"的观察一致：在 L0/L1 任务里，只有 SKILL.md 正文会影响行为。

## 人工核对

按计划对照原始工具调用逐条核对了以下运行：

- **T-A1**：第 2 步用 heredoc 同时写入 `export.py` 与测试，同一命令末尾才运行测试（7 个通过）；此前没有运行过任何东西。
- **T-A2**：第 2 步 Write `export.py`，第 5 步才第一次运行测试。
- **T-A3**：第 2 步先运行现有测试（3 个通过），第 3 步一并写产品与测试。
- **T-B1**：第 2 步 Write 测试，第 3 步运行（7 个失败、1 个错误），第 4 步 Write `export.py`。
- **T-B5**：第 2 步 heredoc 写测试后在同一命令运行（5 个失败），第 3 步写产品。

其余运行的"首次运行"与"首次修改产品"序号与分析器一致。本轮没有发现分析器误判，没有修订评分方法。

## 与第一轮的差异和限制

- 本轮 Skill 由原生方式加载，提示只有 `/veriflow ` 加请求原文；第一轮有一段说明工作目录与限制的模板。两轮结论方向一致，说明第一轮的执行方式偏差没有改变主要观察。
- 本轮用 `--setting-sources project,local`，不加载用户级插件；第一轮在完整会话环境中运行。
- 汇总脚本 [summarize.py](summarize.py) 是冻结后写的，只负责制表，不参与评分。
- 覆盖范围与第一轮相同：单一模型、两个小任务；没有 L2 任务和子代理委派；题目对两组都偏容易。

## 对 Skill 维护的含义

1. **"先写验收检查"的效果在两轮中稳定出现**：仅限 L1，合计 7/7 对 0/7。代价是 L1 的耗时和成本上升约 15–30%。如果这个代价不可接受，可以考虑只对新功能要求"先写新检查"，对已有失败用例的修复保持现状。
2. **B 组让"修改前先运行"更稳定**：L1 上 5/5 对 3/5。这是本轮新增的观察。
3. **两轮都没有执行者读取 references**。需要影响 L0/L1 行为的规则必须写进 SKILL.md 正文。第 2 项收拢到 references 的细则（L2 记录方式、完整性细节）在这类任务里不会被看到；这对 L2 是否成立，需要用 L2 任务验证。
