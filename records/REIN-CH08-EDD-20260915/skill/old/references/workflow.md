# 执行流程

本文件是详细操作说明。核心约束仍以 `SKILL.md` 为入口；只有进入首次执行、恢复、复杂协作或交付门槛时才需要读取这里。

## 首次执行

### 1. 检查环境与授权

先读取当前目录、适用的 `AGENTS.md`、仓库边界、Git 分支/HEAD/worktree 状态、现有测试和任务记录。区分四件事：用户要求的结果、可修改范围、已授权的动作、环境实际能力。

用几行向用户报告范围和验收计划，然后持续执行。除非缺失信息会改变用户场景、外部行为、接口语义、验收、范围或权限，不要停在计划阶段。

### 2. 判断需求是否支持实现决策

以下六项应达到“足以做下一项不可逆决定”，不要求写成长文：

- 用户或受益方是谁；
- 在什么场景使用；
- 当前问题或待验证不确定性；
- 预期结果；
- 本次范围与非目标；
- 什么结果可接受。

缺关键项时，提出少量、针对性的询问，并可并行做不会越权的搜索或头脑风暴。不要用“先做一个完整产品再看”替代澄清。

探索任务必须写明：`HYP-*` 假设、验证方法、时间/次数/成本预算、退出条件以及结果如何改变后续决策。探索通过只表示指定不确定性下降。

### 3. 建立来源

用 `SRC-*` 记录来源及性质：

- `user_requirement`：用户明确要求；
- `user_feedback`：用户对现有结果的反馈；
- `reproduced_defect`：已复现缺陷；
- `external_material`：文档、检索或外部事实；
- `agent_inference`：代理推断或设计建议；
- `implementation_adjustment`：不改变外部约定的必要实现调整。

记录采纳状态。外部材料与代理建议能支持判断，但不能把 `push`、`merge`、`deploy` 等动作变成已授权。

### 4. 先拆独立主任务

复杂需求按用户场景和可观察结果拆成 `MT-*`，不要先拆“前端/后端/数据库”或文件清单。每个主任务写：来源、目标、范围、非目标、依赖、假设。独立是指能单独说明价值和验收，不要求零依赖。

做一次边界/依赖审查：检查重叠所有权、共享接口、先后关系、数据迁移和整体失败模式。另保留一个整体端到端验收，不把“每个子项过线”当成系统通过。

### 5. 主任务确定后定义指标

为整体与每个主任务建立 `MET-*`。每项包含类型、基线、目标或门槛、测量方法、环境/数据、证据位置和判定状态。指标类型与“不造数字”的规则见 [metrics-and-evidence.md](metrics-and-evidence.md)。

如果不知道基线，把“测量基线”作为先行任务；如果无法观测，把“补充观测”作为必要支撑任务。不要假装它们已经通过。

### 6. 准备干净任务工作树

实施新主任务前：

1. 记录明确的基线提交；
2. 检查实际 worktree；
3. 标记现有改动的所有者；
4. 若原目录脏，先在不写入的情况下向用户说明并询问归属；用户同意后，才从明确提交创建隔离 worktree；
5. 不丢弃、不 stash、不打包提交无法确认归属的改动。

如果任务必须依赖未提交内容，先确认是谁的改动、哪些路径纳入本任务、如何在最终提交中保持可审查。

### 7. 再拆实现任务

每个 `IT-*` 写明：所属主任务、来源、任务范围、文件范围、接口兼容约束、依赖、验收指标或必要支撑原因、证据和所有者。

可用且获准时，主线程把源码实现优先交给自定义 coder 子代理；主线程保留架构、共享约定、状态摘要、diff 审查和集成验收。给每个写代理互斥文件范围，不并发修改共享状态文件。

组织上，一个边界清晰的主任务对应一个主要执行会话；复杂需求保留总协调会话维护共享决策、依赖和集成。同一主任务的修正继续留在原会话。这只是组织建议，不自动授权创建任务、会话或代理。

### 8. 实现、审查、集成

实现期间持续检查实际 diff。新行为、接口语义、验收或范围变化必须暂停相应实现，回到来源/主任务层记录原因和影响；普通实现细节可自主决定。

验证时：

- 逐项记录 `passed`、`failed`、`undetermined`；
- 亲自读取或运行证据，不把代理回复当独立验收；
- 先跑受影响检查，再跑整体端到端验收；
- 证据绑定当前补丁或提交状态；验证后修改会使相关证据过期；
- 失败时修实现或重新决策，不降低门槛、不修改测试迎合实现。
- 每个已划分子任务完成后按 [references/delegation-and-handoffs.md](delegation-and-handoffs.md) 的“子任务完成回报”立即回报；主线程核查后在当次进度更新告知用户，并更新 `task-summary.md` 或状态记录。
- 文档同步按 [references/delegation-and-handoffs.md](delegation-and-handoffs.md) 的写作规则执行；未同步的相关文档仍属未完成。

证据因后续修改失效时，按 [records.md](records.md) 的映射把证据、指标、实现任务、主任务与整体验收退回可诚实描述的状态，再重跑受影响检查；不能只把 revision token 刷新为当前。

### 9. 按权限推进交付

门槛按阶段分开：

| 阶段 | 必要条件 | 不应偷带的动作 |
| --- | --- | --- |
| 本地提交 | 当前 diff 已审查；本地强制门槛与整体验收通过；`commit` 已授权 | 远程 CI、推送 |
| 推送 | 本地提交存在；worktree/记录处于预期状态；`push` 已授权 | 合并、部署 |
| 合并 | 远程 CI 实际通过；审查/分支保护满足；`merge` 已授权 | 部署 |
| 部署/发布 | 合并与发布门槛满足；恢复策略就绪；`deploy` 已授权 | 未授权生产变更 |

本地提交门槛不依赖远程 CI，避免“必须先提交才有 CI、但提交又等待 CI”的循环。远程 CI 没跑过时只能报告本地等价检查。

尽早添加能调用真实检查的最小 CI；CD 只在产品与授权条件成熟时添加。发布后核验实际关键行为，流水线成功不等于产品验收。

## 恢复执行

恢复时按以下顺序，不从头脑中的计划续写：

1. 找到任务摘要、结构化状态和最近日志；
2. 核验当前路径、仓库、分支、HEAD、worktree 与基线；
3. 检查证据文件是否存在、版本是否仍匹配；
4. 对照 action/交付记录与外部实际状态，区分“计划、已执行、已验证”；
5. 只重跑安全且必要的验证；对提交、推送、迁移、合并、部署使用动作 ID/回执防重；
6. 更新权威摘要后再继续原主任务。

读取上下文按“索引 → 当前任务摘要 → 与下一步相关的详情/证据”渐进展开；除非核验确有需要，不默认扫描全仓库与完整历史。

若记录与实际环境冲突，以核验后的实际状态为准并追加一条纠偏日志；不要静默改写历史。涉及数据或发布时，恢复策略至少包含备份/快照位置、回滚触发条件和负责人。

## 状态保存点

在以下事件后更新权威摘要，并向追加日志写一条事件：开始、完成、阻塞、重大需求变化、交接、关键实验、提交/推送/合并/部署、暂停或换会话。

摘要只保留当前真相；日志保留“发生过什么”。同一主任务的修正留在原执行会话。交接包仅在确实需要下一位执行者继续时创建。只有用户明确要求创建新任务或会话时才调用相应工具；会话策略本身不构成授权。

子任务完成是即时进度保存点：按委派与交接规则先回报并核查，再更新用户可见进度和已有摘要；不要等全部子任务完成后集中汇报。
