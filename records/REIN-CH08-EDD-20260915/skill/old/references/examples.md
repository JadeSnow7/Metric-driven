# 简短示例

## L0：已定位的小缺陷，直接修并简短汇报

用户说：“`paginate()` 翻到最后一页时总少一条，`tests/test_paging.py::test_last_page` 挂了，帮我修一下。”

问题、位置和验收（那条失败的用例）都已明确，也没有要求提交，属于轻量任务。先看 `git status`，核实成因（例如用 `total=21, size=10` 手算最后一页的切片范围），修改实现而不是断言，选能区分正确修复的检查点（整除与不整除两种总数），然后按结果、依据和限制的阅读顺序汇报：

> **改法**：`paging.py` 计算总页数时把 `total // size` 改为向上取整，最后一页不再被丢掉。
> **检查**：`pytest tests/test_paging.py -q` → 7 passed（此前 1 failed）；另补测 `total=20, size=10`（整除）仍是 2 页。完整测试集未运行。
> **限制与行为变化**：总数能被页大小整除时结果不变；本次没有改变 `size=0` 的输入契约，专门针对该输入的检查未运行。

不需要建立 `records/`、编号或指标表。如果修复过程中发现需要改接口语义或会影响其他模块，再升级到 L1 并说明原因。

## 模糊请求：先澄清，不生成实现承诺

用户说：“给后台加一个智能搜索，要快一点。”

此时至少缺少使用者、搜索对象、当前问题、可接受结果和数据环境。正确下一步不是先建向量库，而是询问少量会改变方案的问题，例如：主要用户要找什么、现有搜索最常失败在哪里、是否允许外部服务、怎样的响应与结果算可接受。

若用户同意先探索，可建立 `HYP-001`：“混合检索能改善已知失败查询”；预算限定为一份固定查询集与两种实现对比，退出结果只回答是否值得进入产品实现。

## 复杂请求：先按结果拆主任务

用户要求“导入旧系统数据、提供新查询接口、上线后可回滚”。先拆为：

- `MT-001`：用户历史数据可完整、可核对地进入新系统；
- `MT-002`：调用方可通过兼容接口取得正确结果；
- `MT-003`：上线失败时可恢复到已知状态；
- 整体验收：从旧数据样本导入到查询，再执行一次演练回滚。

之后才分别建立完整性门槛、接口兼容门槛和恢复门槛，再拆迁移脚本、接口实现、监控等 `IT-*`。不要把“写数据库脚本 / 写后端 / 写 CI”直接当主任务。

## 恢复任务：先核验副作用

摘要写“已推送”，日志有 `ACT-003` 和远程回执，但本地分支落后。恢复者先核验本地 HEAD、远程分支与回执，再决定拉取或继续；不能因为当前工作区看不到提交就再次推送。

如果证据仍标记 `passed`，但 revision token 与当前补丁不同，状态应先变为 `stale`，重跑受影响检查；不能直接从“上次通过”恢复到提交或部署。
