1. 冻结 evaluator 对普通消息的估算漏掉实际 camelCase `toolCallId/toolCalls`，来源检查又只接受 user role。原失败全部保留，不能据此判 C 估算错误或 B 无依据。补充 v4 只适配这两点，哈希绑定原 evaluator；主线程读代码并实际运行三项校准测试，检查 tool-only 来源、手算 171/174、陈旧来源和错误质量。统一应用同一适配器，B/C 默认 16 行通过，A 因超过预算失败。A 的估算值本身正确，实际超限值为 3813、2418、3798、2403、3855、2460、3777。见 root-supplemental-v4 和 root-wire-analysis.json。
2. 三组真实事实变更输出均使用新值，排除了完全预置事实答案；但 task-01 的质量仍为 1，应为 0.5。改写副本的 tasks.json 仍要求 JSON Lines。主线程逐行检查已运行原始输出、当前资料及旧 oracle，均命中 CHECK_QUALITY_EXACT。见 root-supplemental-v4/mutation-adjudication.json。三组按 task ID/claim 数计分的源码解释了此问题；A 未知题还给 0。
3. 两名评审均发现或记录了窗口/检索问题。主线程核对源码：三组检索按索引关键词，未按正文段落评分；A 没有预算裁剪，B/C 以文档或工具消息为裁剪单位。B 的“全通过”结论不成立。
4. Reviewer 2 曾猜错独立入口名称，并在外层 shell 提前展开 Larch 的 PWD。正确 README 命令后续退出 0；旧记录是评审方法失败。Reviewer 1 对这些入口已有实际通过记录。不能将其判产品失败。
5. 正文原文已提取，两名评审实际跟做关键命令。B/C 练习存在占位路径、缺少独立复制/修改步骤；C 仅约 73 行的机制概述，未讲清真实正文检索。A 的练习准备较具体，但行为和质量说明与代码不一致。评审手工补齐步骤后的命令退出 0，不等于最终 Markdown 自足且结论正确。Reviewer 2 Larch 事实改写因 ENOSPC 无有效记录，单列未验证；Reviewer 1 的实际变更输出可用于主线程裁决，不能冒称两次独立通过。
