# 简短示例

## L2：1.3 Spec 绑定记录片段

复杂任务的 1.3 状态把规范索引与运行回执分开：

```json
{
  "schema_version": "1.3",
  "spec": {
    "version": "SPEC-1",
    "authority": "state.spec",
    "source_ids": ["SRC-001"],
    "goal_ref": "discovery.expected_outcome",
    "scope_ref": "discovery.scope",
    "constraints": [], "exceptions": [], "open_items": [],
    "conditions": [{"id": "SC-01", "metric_ids": ["MET-01"], "deliverables": ["docs/result.md"]}],
    "contracts": []
  },
  "binding": {"receipt_paths": ["records/TASK-001/evidence/run.json"]}
}
```

回执内容变化不改变 Spec digest；新增或修改条件、指标规范字段、契约文件字节或交付分类会使当前绑定失效。缺少 1.3 绑定的历史记录保留原样并标为旧语义审计，不能只修改外层版本字段来伪造重跑。

## L0：已定位的小缺陷，直接修并简短汇报

回到 L0 示例时，用户说：“`paginate()` 翻到最后一页时总少一条，`tests/test_paging.py::test_last_page` 挂了，帮我修一下。”

问题、位置和验收（那条失败的用例）都已明确，也没有要求提交，属于轻量任务。先看 `git status`，运行那条失败用例复现缺陷，并把整除与不整除两种总数定为复验检查（`total=21, size=10` 应有 3 页，`total=20, size=10` 应有 2 页）。核实成因后修改实现，保持预期不变并复跑同一检查，然后按结果、依据和限制的阅读顺序汇报：

> **改法**：`paging.py` 计算总页数时把 `total // size` 改为向上取整，最后一页不再被丢掉。
> **检查**：`pytest tests/test_paging.py -q` → 7 passed（此前 1 failed）；其中整除情形 `total=20, size=10` 仍是 2 页。完整测试集未运行。
> **限制与行为变化**：总数能被页大小整除时结果不变；本次没有改变 `size=0` 的输入契约，专门针对该输入的检查未运行。

不需要建立 `records/`、编号或指标表。如果修复过程中发现需要改接口语义或会影响其他模块，再升级到 L1 并说明原因。

## 模糊请求：先澄清，不生成实现承诺

用户说：“给后台加一个智能搜索，要快一点。”

此时至少缺少使用者、搜索对象、当前问题、可接受结果和数据环境。正确下一步不是先建向量库，而是询问少量会改变方案的问题，例如：主要用户要找什么、现有搜索最常失败在哪里、是否允许外部服务、怎样的响应与结果算可接受。

若用户同意先探索，可建立 `HYP-001`：“混合检索能改善已知失败查询”；预算限定为一份固定查询集与两种实现对比，退出结果只回答是否值得进入产品实现。

## 复杂请求：先按结果拆主任务

用户要求“导入旧系统数据、提供新查询接口、上线后可回滚”。先拆为：

- `MT-001`：用户历史数据可完整、可核对地进入新系统；
- `MT-002`：调用方可通过兼容接口取得正确结果；
- `MT-003`：上线失败时可恢复到已知状态；
- 整体验收：从旧数据样本导入到查询，再执行一次演练回滚。

之后才分别建立完整性门槛、接口兼容门槛和恢复门槛，再拆迁移脚本、接口实现、监控等 `IT-*`。不要把“写数据库脚本 / 写后端 / 写 CI”直接当主任务。

## 恢复任务：先核验副作用

摘要写“已推送”，日志有 `ACT-003` 和远程回执，但本地分支落后。恢复者先核验本地 HEAD、远程分支与回执，再决定拉取或继续；不能因为当前工作区看不到提交就再次推送。

记录里 `ACT-004`（`migrate`，目标 `db:staging`）停在 `in_progress`，说明上次会话可能在迁移途中中断。恢复者先查询 staging 数据库的迁移版本表：已经是目标版本就把动作改为 `completed` 并写入版本号作为回执；仍是旧版本时，继续核对迁移日志、部分写入和仍在运行的进程；确认失败且重试安全后改为 `failed` 并写明核验结果，再运行 `--gate action --action migrate --target db:staging` 后重试。在核验之前，门槛会报 `ACTION_OUTCOME_UNKNOWN` 阻止重做。

如果执行记录内的 revision 与当前内容不同，校验器会报 `EXECUTION_REVISION_STALE`；重跑受影响检查、换上新记录，不能直接从“上次通过”恢复到提交或部署。

## 过程证据：提示不等于自动触发

某次回放出现了“已验证”提示，但没有入口调用、分支事件或非空样本。该材料最多证明提示被显示；对自动触发的断言，应补采集真实工具/时序记录。若只能主动执行验证命令，报告写明“主动执行”，不宣称产品自动触发。

## 异常残余与后续合法记录

解析器输入为“未闭合记录的续行 + 下一条合法记录”。若异常续行被误入库，仍需检查后续合法记录是否保留并独立解析；分别记录两条输入的期望和实际状态。单次合法样本通过不能证明任意后续记录都能恢复。

## 工作区里有别人的改动

`git status` 显示 `docs/roadmap.md` 有未提交修改，本任务只改 `src/paging.py` 和对应测试。两者不重叠，所以直接在原目录继续：L0/L1 在汇报里说明检查时该文件有他人改动；L2 把它写进 `baseline.foreign_paths`。提交时先 `git add -- src/paging.py tests/test_paging.py`，再 `git commit -m "fix last page" -- src/paging.py tests/test_paging.py`，不把 `docs/roadmap.md` 带进去。只有本任务也要改 `docs/roadmap.md` 时才先问用户。

## 验证环境不可用

性能基准需要的专用机器今天无法访问，功能测试与原定整体验收场景已有当前通过证据，用户说“先提交，基准等机器恢复后在 CI 上跑”。该性能指标属于 `mandatory_gate`；把它记为 `deferred`，`decision_id` 指向记录这句话的 `DEC-*`。可在本地提交门槛通过后提交；推送仍需已有或新增的 `push` 授权。报告把该指标列为“未验证”；在基准结果出来之前，合并门槛会报 `METRIC_DEFERRED_BLOCKS`。用户没有这样决定时，指标保持 `undetermined`，提交门槛照常阻断。

## 实现完整性与部分验收的判定例

以下是规范解释用例，不是实际 Agent 实验或执行效果证据。规则见 [design.md](design.md) 与 [metrics-and-evidence.md](metrics-and-evidence.md)。

| 情形 | 判定与核查 |
| --- | --- |
| 应用功能组件单测通过，约定按钮未调用它 | 未满足接入承诺；从应用入口核对调用及结果，不能仅凭组件存在通过 |
| 写入操作固定返回成功，或只记日志、吞掉失败 | 未满足契约效果；观察实际写入和失败传播，成功文本不能作为完成证据 |
| 查询确实无匹配记录，或重复操作按契约不再写入 | 合法空结果或幂等无操作；用输入、状态与结果支持，不能按空函数形状判错 |
| 原型只承诺本地演示，外部发布明确不在范围 | 演示入口可验收；发布占位须明确不可用语义与完成条件。本次承诺的演示不能靠注释或禁用按钮豁免 |
| 静态搜索没有调用，但配置动态注册该实现 | 先核对配置和动态入口；未确认失效不得删除，无关发现只报告 |
| 库公开 API 或新项目本次建立的入口完成契约 | 从该入口取得效果证据；只有承诺应用集成才另证应用入口 |
| 原定整体场景确实通过，性能指标经用户决定延期 | 部分验收，校验器给出 `spec_satisfaction=partial`；性能仍未验证，报告写明验证计划 |
| 原定整体场景因缺环境无法运行 | overall_acceptance 保持 undetermined，验收阻断；指标延期不能改成 passed 或删减原场景 |
