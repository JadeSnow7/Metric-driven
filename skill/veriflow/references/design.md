# 设计说明

设计说明把 Spec 的成功条件与实现合同连接起来。Spec 保留目标与验收含义，计划/设计只说明实现方法，指标说明如何测量，证据用于逐项判定；三者不能互相替代。设计深度按结构影响选择：局部改动用几句确认现有边界与验证；跨模块或 API 改动补充简短设计说明；状态、协议或迁移改动补齐适用的失败路径、兼容策略和回退条件。说明放在已有摘要或合同中，记录档位与设计深度分别判断。

## 设计顺序

1. 读取现有边界，记录受影响模块、调用链、数据流和当前失败语义，形成 L0 检查结果。
2. 先沿用项目已有结构区分运行调用链与源码依赖方向：运行调用链记录谁调用谁；源码依赖按项目约定排列。采用依赖倒置时，让领域或应用层声明端口，基础设施实现端口，入口负责装配；为每条跨层调用标出入口、出口和所有权。
3. 按职责、变化原因和数据所有权拆分模块。明确各模块的输入、输出及所拥有的数据；用当前需求和实际调用关系支撑抽象。把跨模块协调放在明确的编排位置，共同变化的规则放在同一归属下。
4. 为受影响 API 确定权威契约来源与维护模块：HTTP API 可采用项目现有 OpenAPI，内部接口可采用公开类型或协议定义。列出消费者、派生类型、文档、示例和测试。变更时先更新权威契约，再按项目方式生成或同步派生内容，并运行消费者与契约检查。
5. 涉及状态时，描述状态的所有者、允许转换、并发控制、可见结果和失败语义；按实际涉及情况为超时、重复、取消、部分完成和恢复写出处理路径与可观察证据。
6. 涉及协议或迁移时，描述版本、兼容窗口、读写顺序、失败检测、回滚或前向修复路径，并把实际适用的门槛与运行环境写入验收。
7. 把设计约束、契约来源与消费者、状态归属和验收方法写入实现合同，再拆分给实现者。实现者沿合同执行，审查者沿同一字段核对。

## 短设计说明模板

按本次影响选取字段，已有信息引用其权威位置。局部修复在回报中说明边界与检查即可。幂等、失败处理等沿用现有约定，关键行为待定时按 SKILL.md 的需求决策表澄清。

```text

消费者、文档与测试：
状态所有者、并发与失败语义：
兼容、迁移与回退路径：
验收方法与证据：
```

## 短例与验收

以“增加逐条返回结果、重复请求幂等且兼容现有客户端的批量取消 API”为例：订单模块拥有取消规则和状态写入，现有应用服务承担批量编排；沿用项目 OpenAPI 作为权威契约，列出 Web、CLI 和契约测试等实际消费者。先确认幂等标识、作用范围及部分失败语义，再定义逐条结果与输入的对应关系。按受影响契约和行为回归旧客户端；数据结构变化时增加迁移验证。若现有协议包含超时恢复机制，将其对应路径纳入验收。

验收按实际约定和现有机制选择检查项：结构图或边界清单覆盖调用者与被调用者；契约搜索结果覆盖受影响消费者、文档和测试；涉及状态时，按已约定行为检查并发、重复、超时或部分失败；涉及旧消费者或协议时，按受影响契约与行为安排兼容回归，即使数据结构保持不变；涉及迁移时，失败路径产生可定位的状态、回滚或修复证据。每项检查记录命令、输入、输出、退出码和对应 revision。

## 实现合同接入点

Spec 条目就绪后，再完成设计说明并拆分实现任务；指标引用 Spec 的成功条件，不另立目标权威。实现合同按结构影响填写适用的设计约束、契约权威来源与消费者、状态归属与失败语义、兼容或迁移条件、验收方法和证据路径；L0 用几句边界与验证记录完成合同。合同就绪后进入实施；L2 中需防重或外部核验的交付动作按 [workflow.md](workflow.md) 的对应门槛与 `ACT-*` 状态执行。`in_progress` 表示动作正在执行、结果仍待核验，执行结束后立即写入结果与回执。
