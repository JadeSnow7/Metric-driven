# 执行流程

本文件用于首次完整执行、恢复任务、复杂协作和交付门槛。核心规则见 `SKILL.md`。

## 首次执行

### 1. 检查现状

读取当前目录及适用的 `AGENTS.md`、`CLAUDE.md`，核对仓库、分支、HEAD、工作区、现有契约、测试、任务记录、授权与环境能力。保留未提交内容，确认基线与文件所有权；按 [design.md](design.md) 确认交付入口及当前接入状态。Git 长时间无响应记为 `undetermined`；无关改动记录为 `baseline.foreign_paths`，不阻断互斥范围内工作。

### 2. 形成 Spec 并检查就绪

按实际性质把来源分类为 `SRC-*`（用户要求、反馈、复现缺陷、外部材料、代理建议、实现调整），再把用户意图与既有需求、指标、设计合同和验收字段归并为当前 Spec（L0 可留在对话，L1 放入摘要，L2 使用稳定文件和条目）。Spec 是目标、范围、成功条件、约束、异常语义和验收方法的唯一任务入口；接口字段引用项目 OpenAPI、公开类型或协议定义的权威位置。仅 L2 保存 Spec 内容指纹并单独列出产品输入和运行回执路径。委派前确认条目、范围、约束、交付物、验证方法和证据位置齐全；缺项由主线程补齐。产品或 Spec 相关内容变化时，旧证据重新做适用性检查，无法证明不受影响则重验；历史结果保留并标记适用性。

### 3. 设计计划与实现合同

按结果拆 `MT-*`，写明来源、目标、范围、依赖与假设；指标入口见 [metrics-and-evidence.md](metrics-and-evidence.md)。再按 [design.md](design.md) 选择设计深度，明确入口与实际执行路径、职责、契约来源、消费者、状态或副作用归属、兼容语义、计划与验收。计划描述实现方法，指标定义测量，证据支持判定。每个 `IT-*` 写明 Spec 条目、可写路径、基线、依赖、验收和证据位置。主线程维护架构、共享约定和状态；各写入者拥有互斥路径。

### 4. 先写验收检查

术语：「验收检查」指本节从 Spec 推导、在实现前后运行的同一组检查；「基线」只指 Git 基线（`baseline.*`）和指标测量起点（`MET-*.baseline`）；「基准」只指性能 benchmark。

在修改产品代码或交付物之前，从 Spec 写出可复跑的检查：关联的成功条件、代表性输入与异常边界、预期结果、命令或人工步骤，以及环境和证据位置。复用项目现有测试框架；现有检查不足时先补测试或复现脚本。文档和视觉任务可用审阅清单，不为形式新增测试工程。

L0 只需在对话中指明复验所用的现有检查或一句人工步骤；缺陷修复先运行复现并留下结果，其他 L0 不要求实现前运行。

L1/L2 先在未修改的产品上执行这些检查，保存命令、原始结果及版本。缺陷修复应复现目标缺陷，新功能应显示尚未满足的成功条件；已有行为的回归检查可以通过，不刻意制造失败。确认失败来自目标行为，而非环境、依赖或测试本身。性能改动先固定数据、配置和测量口径，采集可比较的基线。

主线程核对验收检查与 Spec 一致且具备区分能力后，才进入产品实现。环境无法执行时记为 `undetermined` 或未运行，说明原因；先完成可执行的替代检查并判断是否足以支持实施，无法建立有效检查的部分保持阻塞，继续独立工作。实现后补测不能冒充实现前结果；恢复任务缺少实现前结果时如实记录，对后续改动先写检查。

验收检查的编写与运行可作为独立子任务委派；合同明确产品实现依赖其完成与主线程核查。L0/L1 留存于对话或摘要；L2 按 [metrics-and-evidence.md](metrics-and-evidence.md) 的“L2 实现前证据的记录方式”登记执行证据，不新增平行的 Spec 或状态体系。此顺序由执行者、审查者与主线程核查，现有机械门槛不自动证明测试早于实现。

### 5. 实现、观察与验证

沿合同实现后先复跑同一验收检查，再完成受影响回归和整体端到端验收。对照合同检查实际 diff，核对模块边界、接口消费者、状态归属与兼容路径。新规格问题按入口决策表处理。

复查实际 diff 时，确认领域命名和控制流清晰，数据及状态变化显式；确认注释解释意图与约束，模块职责和状态归属明确；按 [design.md](design.md) 检查语义空实现、占位边界和替换后的清理，核对约定入口实际接通；对新增复杂性或层级，确认其有当前需求或实际变化支撑并带来实际收益。发现问题时记录具体位置，以及对理解、修改或验证的影响；L0 也执行这项按比例的复查。

- L2 用 `record_execution.py --repo --state` 保存命令、输出、revision、Spec 内容指纹及状态；`--state` 必须提供。L0/L1 按档位在摘要或回复留存命令和结果。读取原始证据后判定 `passed`、`failed` 或 `undetermined`。
- 复杂验证先校准目标对象、输入是否到达、触发路径和观察窗口；必要时加入正负对照或反例，确认检查能区分正确与错误行为。轻量任务仍按档位记录，不因此建立额外清单。
- 失败时按契约修实现；用户改变要求时先更新 Spec 和验收。同类缺陷再次出现时复查合同、验收方法和拆分边界。内容变化后重跑受影响检查，将旧证据标为 `stale`，用新的实际执行记录绑定当前内容。子任务完成后按 [delegation-and-handoffs.md](delegation-and-handoffs.md) 回报并核查，受影响文档和示例同步后再完成该交付。

### 6. 逐项判定

报告前逐项核对 Spec 明确列出的交付物、有效证据和未满足项；仅当 Spec 列明正文、示例或运行产物为交付物时，缺任一项才只能报告部分完成。分别报告 Spec 满足情况、指标延期、整体验收、记录完整性和动作状态。完整完成与部分验收按 [metrics-and-evidence.md](metrics-and-evidence.md) 的“完整完成与部分验收”判定。

### 7. 按授权交付或继续迭代

| 阶段 | 执行条件与结果 |
| --- | --- |
| 验收 `acceptance` | 当前 diff 已审查；整体验收有当前通过证据；强制指标通过，或经用户决定延期（报告为部分验收） |
| 本地提交 | 验收及 `commit` 授权就绪，重复动作核查通过；提交审查过的指定路径 |
| 推送 | 当前内容已提交，提交路径已审查，`push` 授权与目标匹配；保存远端回执 |
| 合并 | 目标提交已推送，其远程 CI 实际通过，`merge` 已授权；保存合并结果 |
| 部署/发布 | 合并完成，恢复策略就绪，`deploy` 授权与环境匹配；核验上线行为 |
| 迁移等自定义动作 | 对应授权、目标、强制验证与恢复策略就绪；运行 `action` 门槛并保存结果 |

L2 中需防重或外部核验的交付动作按 `planned → 对应门槛通过 → in_progress → 执行 → completed/failed` 推进。`ACT-*` 包含 target 与 revision；`in_progress` 表示正在执行且结果待核验，执行后立即记录结果与回执。动作状态的具体校验见 [metrics-and-evidence.md](metrics-and-evidence.md)。

本地提交使用本地验收证据，远程 CI 核验绑定实际提交。环境受限且用户决定先交付时，按 [metrics-and-evidence.md](metrics-and-evidence.md) 的“环境不可用与延后验证”处理。

指定路径提交使用 `git add -- <paths>` 后 `git commit -m <message> -- <paths>`。CI 调用实际检查；发布流程按产品需求和用户授权建立，发布后核验关键行为。

## 恢复执行

1. 读取任务摘要、结构化状态与最近日志，并核对当前 Spec 的位置、版本/内容绑定和受影响条目。
2. 核验路径、仓库、分支、HEAD、worktree 与基线。
3. 检查证据存在性及版本匹配。
4. 核验 `ACT-*` 与外部状态：提交查日志，推送查远端引用，迁移查目标版本表，部署查发布记录。对 `in_progress`、`unknown` 动作先查实际结果，再更新状态与回执；外部已发生的动作补入记录。
5. 运行必要验证，各副作用动作先过对应门槛；按目标与版本识别重复动作。
6. 更新权威摘要后继续主任务。

按“索引 → 当前摘要 → 下一步相关详情”展开上下文。记录与实际状态冲突时，以核验结果为准追加纠偏日志。数据或发布恢复策略写明备份/快照、触发条件和负责人。

## 状态保存点

开始、子任务完成、阻塞、重大变化、交接、关键实验、副作用动作和暂停后，更新摘要并追加事件。摘要保存当前状态，日志保存历史。交接包按下一执行者所需内容建立；同一主任务的修正延续原会话，新会话按用户请求创建。
