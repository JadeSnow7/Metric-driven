# 执行流程

本文件用于首次完整执行、恢复任务、复杂协作和交付门槛。核心规则见 `SKILL.md`。

## 首次执行

### 1. 检查现状

读取当前目录及适用的 `AGENTS.md`、`CLAUDE.md`，核对仓库、分支、HEAD、工作区、现有契约、测试、任务记录、授权与环境能力。保留未提交内容，确认基线与文件所有权。Git 长时间无响应记为 `undetermined`；无关改动记录为 `baseline.foreign_paths`，不阻断互斥范围内工作。

### 2. 形成 Spec 并检查就绪

按实际性质把来源分类为 `SRC-*`（用户要求、反馈、复现缺陷、外部材料、代理建议、实现调整），再把用户意图与既有需求、指标、设计合同和验收字段归并为当前 Spec（L0 可留在对话，L1 放入摘要，L2 使用稳定文件和条目）。Spec 是目标、范围、成功条件、约束、异常语义和验收方法的唯一任务入口；接口字段引用项目 OpenAPI、公开类型或协议定义的权威位置。仅 L2 保存 Spec 内容指纹并单独列出产品输入和运行回执路径。委派前确认条目、范围、约束、交付物、验证方法和证据位置齐全；缺项由主线程补齐。产品或 Spec 相关内容变化时，旧证据重新做适用性检查，无法证明不受影响则重验；历史结果保留并标记适用性。

### 3. 设计计划与实现合同

按结果拆 `MT-*`，写明来源、目标、范围、依赖与假设；指标入口见 [metrics-and-evidence.md](metrics-and-evidence.md)。再按 [design.md](design.md) 选择设计深度，明确职责、契约来源、消费者、状态/兼容语义、计划与验收。计划描述实现方法，指标定义测量，证据支持判定。每个 `IT-*` 写明 Spec 条目、可写路径、基线、依赖、验收和证据位置。主线程维护架构、共享约定和状态；各写入者拥有互斥路径。

### 4. 实现、观察与验证

对照合同检查实际 diff，核对模块边界、接口消费者、状态归属与兼容路径。新规格问题按入口决策表处理。验证依次完成受影响检查和整体端到端验收：

- L2 用 `record_execution.py --repo --state` 保存命令、输出、revision、Spec 内容指纹及状态；`--state` 必须提供。L0/L1 按档位在摘要或回复留存命令和结果。读取原始证据后判定 `passed`、`failed` 或 `undetermined`。
- 复杂验证先校准目标对象、输入是否到达、触发路径和观察窗口；必要时加入正负对照或反例，确认检查能区分正确与错误行为。轻量任务仍按档位记录，不因此建立额外清单。
- 失败时按契约修实现；用户改变要求时先更新 Spec 和验收。同类缺陷再次出现时复查合同、验收方法和拆分边界。内容变化后重跑受影响检查，将旧证据标为 `stale`，用新的实际执行记录绑定当前内容。子任务完成后按 [delegation-and-handoffs.md](delegation-and-handoffs.md) 回报并核查，受影响文档和示例同步后再完成该交付。

### 5. 逐项判定

报告前逐项核对 Spec 明确列出的交付物、有效证据和未满足项；仅当 Spec 列明正文、示例或运行产物为交付物时，缺任一项才只能报告部分完成。分别报告 Spec 满足情况、记录完整性和动作状态。

### 6. 按授权交付或继续迭代

| 阶段 | 执行条件与结果 |
| --- | --- |
| 验收 `acceptance` | 当前 diff 已审查；强制指标与整体验收通过，或环境受限的对应指标已按用户决定记为 `deferred` 并关联决定；如实记录通过与延期的部分 |
| 本地提交 | 验收及 `commit` 授权就绪，重复动作核查通过；提交审查过的指定路径 |
| 推送 | 当前内容已提交，提交路径已审查，`push` 授权与目标匹配；保存远端回执 |
| 合并 | 目标提交已推送，其远程 CI 实际通过，`merge` 已授权；保存合并结果 |
| 部署/发布 | 合并完成，恢复策略就绪，`deploy` 授权与环境匹配；核验上线行为 |
| 迁移等自定义动作 | 对应授权、目标、强制验证与恢复策略就绪；运行 `action` 门槛并保存结果 |

L2 中需防重或外部核验的交付动作按 `planned → 对应门槛通过 → in_progress → 执行 → completed/failed` 推进。`ACT-*` 包含 target 与 revision；`in_progress` 表示正在执行且结果待核验，执行后立即记录结果与回执。动作状态的具体校验见 [metrics-and-evidence.md](metrics-and-evidence.md)。

本地提交使用本地验收证据，远程 CI 核验绑定实际提交。环境受限且用户决定先交付时，指标记为 `deferred` 并关联决定；本地提交与推送按门槛执行，合并、部署及其他难以撤销的动作等强制验证完成后推进。

指定路径提交使用 `git add -- <paths>` 后 `git commit -m <message> -- <paths>`。CI 调用实际检查；发布流程按产品需求和用户授权建立，发布后核验关键行为。

## 恢复执行

1. 读取任务摘要、结构化状态与最近日志，并核对当前 Spec 的位置、版本/内容绑定和受影响条目。
2. 核验路径、仓库、分支、HEAD、worktree 与基线。
3. 检查证据存在性及版本匹配。
4. 核验 `ACT-*` 与外部状态：提交查日志，推送查远端引用，迁移查目标版本表，部署查发布记录。对 `in_progress`、`unknown` 动作先查实际结果，再更新状态与回执；外部已发生的动作补入记录。
5. 运行必要验证，各副作用动作先过对应门槛；按目标与版本识别重复动作。
6. 更新权威摘要后继续主任务。

按“索引 → 当前摘要 → 下一步相关详情”展开上下文。记录与实际状态冲突时，以核验结果为准追加纠偏日志。数据或发布恢复策略写明备份/快照、触发条件和负责人。

## 状态保存点

开始、子任务完成、阻塞、重大变化、交接、关键实验、副作用动作和暂停后，更新摘要并追加事件。摘要保存当前状态，日志保存历史。交接包按下一执行者所需内容建立；同一主任务的修正延续原会话，新会话按用户请求创建。
