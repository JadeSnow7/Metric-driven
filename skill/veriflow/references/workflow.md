# 执行流程

本文件用于首次完整执行、恢复任务、复杂协作和交付门槛。核心规则见 `SKILL.md`。

## 首次执行

### 1. 检查环境与授权

读取当前目录及适用的 `AGENTS.md`、`CLAUDE.md`，核对仓库、分支、HEAD、工作区、现有测试与任务记录。分别确认用户要求、可写范围、动作授权和环境能力。简短说明范围与验收计划，持续推进已就绪工作。

### 2. 判断需求是否支持实现决策

确认用户、场景、问题、预期结果、范围与可接受结果。信息足以支撑下一项决定时进入实施；关键缺口按入口的决策表澄清，同时推进独立的搜索与核验。探索记录假设、方法、预算、退出条件与结果如何影响后续决定。

### 3. 建立来源

按实际性质记录 `SRC-*`：用户要求 `user_requirement`、反馈 `user_feedback`、复现缺陷 `reproduced_defect`、外部材料 `external_material`、代理建议 `agent_inference`、必要实现调整 `implementation_adjustment`。同时记录采纳状态；动作授权以用户指令为依据。

### 4. 按结果拆主任务

按用户场景与可观察结果划分 `MT-*`，写明来源、目标、范围、依赖和假设。记录格式中的 `non_goals` 填写“沿用现状的范围”，保留字段名以兼容现有校验器。检查文件所有权、共享接口、先后关系和整体失败模式，为整体保留端到端验收。

### 5. 定义指标

为整体与主任务建立 `MET-*`，写明类型、基线、目标、方法、环境、数据、证据和状态，详见 [metrics-and-evidence.md](metrics-and-evidence.md)。基线未知时先测量，结果不可观测时先补观测，按实际证据判定结果。

### 6. 确认起点并完成设计

记录基线提交与当前工作区，保留已有内容及改动归属。Git 长时间无响应时标为 `undetermined`；可读取文件按快照与哈希核对。无关改动记录为 `baseline.foreign_paths`，在互斥文件范围内继续。与他人改动重叠或存在依赖时，先确认处理方式；已确认依赖的基线记为 `dirty_dependency_confirmed`，相关路径纳入审查。

按 [design.md](design.md) 选择设计深度：局部修复确认边界与检查方法；跨模块/API 变化说明职责、依赖方向、契约权威来源与消费者；涉及状态、协议或迁移时补适用语义。设计写入已有摘要或实现合同，并列出对应验收。

### 7. 拆实现任务

每个 `IT-*` 写明所属主任务、来源、范围、可写路径、适用设计约束、依赖、指标或必要支撑原因、证据和所有者。可用且获准时交给 coder；Claude Code 中使用 Sonnet 的 `veriflow-coder`，见 [claude-code.md](claude-code.md)。

主线程维护架构、共享约定、状态、最终审查与集成验收；各写入者拥有互斥路径。子代理反复停滞时，核查环境并缩小任务范围，仍受阻时由主线程接手，如实记录实现者和审查者。一个边界明确的主任务使用主要执行会话，协调会话维护共享决策；创建新会话按用户明确请求执行。

### 8. 实现、审查、集成

对照合同检查实际 diff，核对模块边界、接口消费者、状态归属与兼容路径。新规格问题按入口决策表处理。验证依次完成受影响检查和整体端到端验收：

- 用 `record_execution.py --repo --state` 保存命令、输出与 revision，读取原始证据后判定 `passed`、`failed` 或 `undetermined`。
- 失败时按契约修实现；用户改变要求时先更新需求和验收。同类缺陷再次出现时，复查合同、验收方法和拆分边界。
- 内容变化后重跑受影响检查，将旧证据标为 `stale`，用新的实际执行记录绑定当前内容。
- 子任务完成后按 [delegation-and-handoffs.md](delegation-and-handoffs.md) 回报并核查，受影响文档和示例同步后再完成该交付。

### 9. 按权限推进交付

| 阶段 | 执行条件与结果 |
| --- | --- |
| 验收 `acceptance` | 当前 diff 已审查；强制指标与整体验收通过，或环境受限的对应指标已按用户决定记为 `deferred` 并关联决定；如实记录通过与延期的部分 |
| 本地提交 | 验收及 `commit` 授权就绪，重复动作核查通过；提交审查过的指定路径 |
| 推送 | 当前内容已提交，提交路径已审查，`push` 授权与目标匹配；保存远端回执 |
| 合并 | 目标提交已推送，其远程 CI 实际通过，`merge` 已授权；保存合并结果 |
| 部署/发布 | 合并完成，恢复策略就绪，`deploy` 授权与环境匹配；核验上线行为 |
| 迁移等自定义动作 | 对应授权、目标、强制验证与恢复策略就绪；运行 `action` 门槛并保存结果 |

L2 中需防重或外部核验的交付动作按 `planned → 对应门槛通过 → in_progress → 执行 → completed/failed` 推进。`ACT-*` 包含 target 与 revision；`in_progress` 表示正在执行且结果待核验，执行后立即记录结果与回执。动作状态的具体校验见 [metrics-and-evidence.md](metrics-and-evidence.md)。

本地提交使用本地验收证据，远程 CI 核验绑定实际提交。环境受限且用户决定先交付时，指标记为 `deferred` 并关联决定；本地提交与推送按门槛执行，合并、部署及其他难以撤销的动作等强制验证完成后推进。

指定路径提交使用 `git add -- <paths>` 后 `git commit -m <message> -- <paths>`。CI 调用实际检查；发布流程按产品需求和用户授权建立，发布后核验关键行为。

## 恢复执行

1. 读取任务摘要、结构化状态与最近日志。
2. 核验路径、仓库、分支、HEAD、worktree 与基线。
3. 检查证据存在性及版本匹配。
4. 核验 `ACT-*` 与外部状态：提交查日志，推送查远端引用，迁移查目标版本表，部署查发布记录。对 `in_progress`、`unknown` 动作先查实际结果，再更新状态与回执；外部已发生的动作补入记录。
5. 运行必要验证，各副作用动作先过对应门槛；按目标与版本识别重复动作。
6. 更新权威摘要后继续主任务。

按“索引 → 当前摘要 → 下一步相关详情”展开上下文。记录与实际状态冲突时，以核验结果为准追加纠偏日志。数据或发布恢复策略写明备份/快照、触发条件和负责人。

## 状态保存点

开始、子任务完成、阻塞、重大变化、交接、关键实验、副作用动作和暂停后，更新摘要并追加事件。摘要保存当前状态，日志保存历史。交接包按下一执行者所需内容建立；同一主任务的修正延续原会话，新会话按用户请求创建。
