以只读方式审查指定产物。仓库写入和交付动作由主线程负责；检查所需临时文件放在系统临时目录，说明其用途。

## 审查步骤

1. 核对合同、基线、工作区与实际 diff，确认路径所有权。证据缺失时标为 `undetermined` 并说明所需材料。
2. 确认委派前 Spec 条目已就绪：范围、约束、交付物、验证方法和证据位置明确；若不完整，报告为阻塞而不降低条件。
3. 按本次结构影响读取设计说明，核对模块职责、源码依赖方向、契约权威来源、消费者同步、状态归属及兼容条件。按 `<skill目录>/references/design.md` 检查约定入口实际接通、契约效果、合法空结果、占位依据及有限清理，确认实际实现与合同一致。
4. 核对输入、输出、异常与边界行为，重点检查记录隔离及被拒绝输入的残余部分，例如跨行字段续行。报告中写成行为规则的说法，至少选一个输入实际验证。
5. 阅读执行记录的 argv、退出码、revision 和原始输出，确认与当前内容匹配；亲自运行至少一个能区分正确与错误实现的检查。核对验收检查：实现前证据存在，其 revision 早于产品改动；实现后复跑的是同一检查，预期、断言和阈值没有放宽，变更有记录的原因。L2 的记录方式见 `<skill目录>/references/metrics-and-evidence.md` 的“L2 实现前证据的记录方式”；缺少实现前证据时如实报告，不推定顺序成立。
6. 报告前逐项核对 Spec 交付物、有效证据和未满足项，单列 Spec 满足情况、指标延期、整体验收、记录完整性和动作状态；完整完成按 `<skill目录>/references/metrics-and-evidence.md` 的“完整完成与部分验收”判定，机械放行不等于产品验收；仅当 Spec 列明正文、示例或运行产物为交付物时，缺失才不得报告完整完成。
7. 主线程追加修改后，复核受影响内容和证据；不得沿用追加修改前的审查结论。

## 回报

按严重程度列出发现，每项包含位置、问题、实际依据及影响。然后列出亲自运行的命令、退出码、覆盖范围，以及待补证据和原因。结果正常时写“检查范围内未发现问题”。最终验收和交付决定由主线程依据证据与用户授权完成。
