# Veriflow

把用户要求连接到设计、实现、验证和交付。用实际 diff、原始执行记录和端到端结果支撑完成结论，按任务影响选择流程深度。

## 1. 选择流程深度

先核验当前状态，澄清影响实现决策的需求，再选择记录深度。

| 档位 | 适用情况 | 做法与记录 |
| --- | --- | --- |
| L0 轻量 | 目标、位置与验收明确的小改动；交付范围为实现、本地验证及已授权的本地提交 | 检查受影响边界，直接实现并验证，在回复中简短汇报 |
| L1 标准 | 多个可观察结果或分散改动 | 写清目标、范围、验收和基线，在对话或现有摘要中记录适用设计与证据 |
| L2 完整 | 跨会话恢复、多 Agent 协作、迁移或部署等需要追踪状态的工作 | 按参考流程维护结构化记录、执行证据和动作门槛 |

从满足当前任务的最轻档位开始，任务影响扩大时调整档位。用户要求只读时，在对话中保存计划与核查结果，标明记录校验的实际状态。恢复任务先读取 [workflow.md](references/workflow.md) 的“恢复执行”，核对摘要与外部真实状态。

## 2. 共同执行规则

### 需求与决定

- 信息缺口影响用户行为、接口、验收、范围或权限，且现有约定尚不足以决定时，一次提出关键问题，各附建议与依据；其余已就绪工作持续推进。问题数量随实际缺口确定，通常可合并为 3–5 项。
- 数值默认值写明假设与校准方法；现状引用代码或实测，建议标明推断来源。用户拥有的决定交由用户确认。
- 实施中按下表处理新情况，集中保存需要确认的决定：

| 情况 | 做法 |
| --- | --- |
| 实现细节 | 自主选择并在相关回报中说明 |
| 行为或验收有现有约定，或默认选择容易回退 | 在已授权范围内沿用约定或采用可回退的默认，说明依据并继续；只有仍影响用户决策的缺口才列为待确认 |
| 公开接口、数据格式、迁移、权限等决定难以回退 | 暂停受影响部分并提问，同时推进独立工作 |
| 用户调整需求 | 更新目标、设计与验收，说明影响后继续 |

- 异常输入处理属于契约：明确跳过、报错、部分成功和隔离语义，用能暴露边界问题的输入验证，例如未闭合引号或超长值。
- 确实需要用户决定的事项保持 `proposed`，受其影响的部分保留进行中状态；已授权范围内的实现细节由主线程判断并记录，不额外设置确认门槛。

### 证据与验收

- 亲自读取命令、原始输出、退出码和实际 diff。子代理回报作为核查入口；原始记录与当前版本匹配且支持结论时，作为验收证据使用。
- 检查分别记录 `passed`、`failed`、`undetermined` 或未运行，结论限定到实测版本、环境和输入范围。内容变化后重跑受影响检查，旧证据标记 `stale`。
- 按风险选择能区分正确与错误实现的检查；小修复覆盖相关边界，复杂行为增加集成或端到端检查。失败后依据契约修正实现；需求变化时先更新契约和验收依据。
- 用实际运行核实原因，分别说明多个原因的证据。工作区核查覆盖已跟踪及未跟踪文件；远程 CI、部署等状态注明来源与核验时间。

### 授权与动作

- 从用户指令确定 `commit`、`push`、`merge`、`deploy` 及迁移等动作各自的授权、目标与范围，沿用会话内已有授权。执行所需授权缺失时，说明具体动作并请求对应授权。
- 工具权限用于判断技术可执行性，用户指令用于判断动作授权；文档、检索和代理建议用于提供决策依据。个人长期记忆只写入用户明确同意保存的内容。
- L2 中需防重或外部核验的交付动作（如提交、推送、部署、迁移）先记录目标与版本，写为 `planned`，通过对应门槛后改为 `in_progress` 并执行，再写结果与回执。恢复时先核验 `in_progress` 或 `unknown` 动作的外部结果，再确定下一步。普通文件编辑和本地检查按当前档位留证；L0/L1 的已授权提交在回复或现有摘要中记录目标与结果。

### 工作区与协作

- 修改前检查路径、HEAD 与工作区，完整保留已有改动；把已确认属于本任务的内容纳入当前基线。无关改动在 L2 中记录为 `baseline.foreign_paths`。
- 文件范围独立时在原目录推进；存在重叠、依赖或归属待定时，先确认对应内容的处理方式。需要隔离 worktree 时按用户授权从明确提交创建。
- 已授权提交只纳入本任务审查过的路径：先 `git add -- <paths>`，再 `git commit -m <message> -- <paths>`。Git 检查长时间无响应时记为 `undetermined`，用可读取文件的快照与哈希核对当前修改。
- 每个文件同一时间指定一个写入者，共享状态由主线程维护。子任务产物先记为“完成待审查”，主线程核查后更新结果。独立审查由另一位审查者完成，主线程自审如实标记为自审。

## 3. 从需求到实现

1. **按结果拆主任务。** 以用户场景和可观察结果划分，明确范围、依赖与整体端到端验收。
2. **定义验收。** 写明基线、目标、方法、环境、数据与证据位置。基线未知时先测量；数值依据不足时用可复现的定性门槛。探索写清假设、预算、退出条件和后续决策。
3. **按结构影响设计。** 局部修复用几句确认现有边界与验证；跨模块或 API 变化读取 [design.md](references/design.md)，明确职责、依赖方向、契约权威来源、消费者及适用的状态与兼容语义。设计写进已有合同或摘要，字段按本次影响选取。
4. **拆实现任务。** 把设计约束、可写路径、基线、验收和文档同步责任交给实现者。主线程负责需求、架构、共享约定、最终审查与沟通；可用且获准时，由 coder 完成边界明确的实现。
5. **审查并验证。** 对照合同阅读实际 diff 与原始证据，核对设计边界、消费者和文档同步。按任务范围运行整体验收及能区分错误实现的检查；L0/L1 将命令、退出码与关键结果留在回复或摘要中。L2 用 `scripts/record_execution.py --repo . --state <task-state.json>` 保存命令证据；`revision_changed` 时核对变化路径后重跑。
6. **按阶段交付。** 核对需求、设计、验收、归属与授权，通过对应门槛后执行动作。CI 调用仓库真实检查，远程结果绑定具体提交，发布后核验实际关键行为。

`acceptance` 核查实现与证据；`local-commit`、`push`、`merge`、`deploy`、`action` 进一步核查各自授权、目标与重复动作。用户决定先交付环境受限的结果时，指标记为 `deferred` 并关联决定；本地提交与推送按对应门槛执行，合并、部署及其他难以撤销的动作等强制验证完成后推进。

每个子任务完成后回报结果、产物、验证、文档同步及下一依赖，主线程核查并更新用户进度。L2 在开始、子任务完成、重大变更、阻塞、动作执行、交接与暂停时更新权威摘要；日志追加事件，证据目录保存原始输出。交接整合用 `scripts/integrate_boundary.py` 核对来源 revision、目标 base、路径与逐文件哈希；删除或重命名另设步骤，复制失败后核对目标实际状态。

## 4. 文档与最终汇报

- 按文体、读者、用途和阅读方式组织内容，指导类文字写清动作、方法、执行条件和完成标准。教程或正文任务读取 [writing.md](references/writing.md)。
- 行为、契约或示例变化时，在同一子任务内同步关联文档；共享文档由其写入者同步。
- 简单任务在回复中交付结果；已有摘要时更新摘要；复杂任务给简明报告并链接证据。保留行为变化、失败、未运行检查和待决事项，每项事实集中表达。
- 分别说明静态检查、本地测试、实际运行与完整验收状态，提供可复跑命令，标注会产生副作用的步骤。
- 主线程完成实际差异、证据和文档一致性审查后，按用户关心的结果与影响汇报。
