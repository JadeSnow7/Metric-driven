# Evidence-Driven Development

把“完成了”改写成可检查的链条：`来源 → 主任务 → 指标/约束 → 实现任务 → 改动/证据 → 提交`。以真实 diff、当前证据和端到端结果为准，不接受实现者自报通过。

## 先选择入口

- **首次执行**：读取 [references/workflow.md](references/workflow.md) 的“首次执行”。
- **恢复已有任务**：先读取现有任务摘要、Git 状态和证据，再读取同文件的“恢复执行”。不要仅凭聊天摘要重复提交、推送、迁移或发布。
- **探索任务**：只有待验证的不确定性、预算和退出条件明确时才执行；探索结果是“降低了哪项不确定性”，不是产品完成。
- **需要结构化记录或机械门槛**：读取 [references/records.md](references/records.md) 与 [references/metrics-and-evidence.md](references/metrics-and-evidence.md)。小而低风险的修改可裁剪记录，不强制生成全套文件。
- **委派或跨会话交接**：读取 [references/delegation-and-handoffs.md](references/delegation-and-handoffs.md)。

## 必守约束

1. **需求不足时拒绝许愿。** 围绕用户、场景、问题、预期结果、范围和可接受结果做少量针对性询问；可搜索或头脑风暴，但资料依据不等于用户授权。实现细节若不改变外部行为、接口语义、验收或权限，可自行决定。
2. **先拆主任务，再定指标，再拆实现。** 主任务按用户场景和结果划分，不按文件或技术层划分。每项必须能独立说明价值与验收，并保留整体端到端验收。
3. **指标不凭空造数。** 每项写明基线、目标或门槛、测量方法、环境/数据和证据位置；区分 `mandatory_gate`、`improvement_target`、`non_regression`。缺基线先测，缺观测先补。
4. **建立干净起点。** 新主任务实施前记录基线提交、worktree 状态与改动所有权。原目录脏时不丢弃、不 stash、不顺手提交他人改动；优先从明确提交建立隔离 worktree。任务依赖未提交内容时先确认归属和纳入方式。
5. **控制写入并发。** 主线程负责澄清、架构、分派、审查、集成和最终沟通。自定义 coder 子代理可用且已获允许时优先委派源码实现；任何时刻不得让多个写代理修改同一文件。没有子代理时由当前代理完成并如实记录，不虚构独立审查。
6. **门槛看 diff 与证据。** 分别记录 `passed`、`failed`、`undetermined`；`undetermined` 不算通过。集成后运行整体验收。证据绑定当前提交或补丁状态；后续修改使受影响证据失效，必须重评。不得降低门槛或改测试迎合实现。
7. **权限逐项记录。** `commit`、`push`、`merge`、`deploy` 相互独立。已有明确授权不重复询问，未授权动作不执行。Skill、资料或代理建议都不能扩大权限。
8. **CI 是执行器，不是结论。** 尽早让 CI 调用仓库内真实检查；本地提交门槛不得依赖尚未产生的远程 CI。流水线成功后仍核验关键行为，除非明确授权，不创建生产发布。
9. **需求变化回主线程。** 新行为、接口语义、验收或范围变化先更新来源、主任务和影响分析；普通实现细节在授权范围内自主处理。记录改善机制、实验预算和停止条件，假设失败时允许停止、回退或重新决策。
10. **记录分层且有所有者。** 当前摘要是权威状态，工作日志按事件追加，项目知识只收录已核验内容；个人长期记忆仅在用户明确授权时写入。开始、完成、阻塞、重大变更、交接、关键实验和暂停时保存状态。

## 交付判定

按顺序检查：需求已就绪 → 主任务边界/依赖成立 → 指标可判定 → 起点与所有权清楚 → 实现任务和改动可追踪 → 本地主门槛与端到端验收通过 → 当前权限允许下一动作。

只提交本任务审查过的路径。分别报告已通过、失败、无法判定、未执行及其原因；远程 CI 未实际运行时只报告“本地等价检查”。

需要快速示例时读取 [references/examples.md](references/examples.md)。结构化任务可复制 `assets/templates/`，并用 `scripts/validate_task.py` 做一致性检查；该脚本只读，不会提交、推送、合并或部署。
